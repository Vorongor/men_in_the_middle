# Крок 02 — Економічний глухий кут: з ями завжди є вихід

**Статус: ✅ виконано** · Виконано: 2026-07-04 · Залежності: крок 01 (✅) · Баг тест-звіту: **№2 (критичний)**
**Вхідні дані:** [alpha_1_0_test_summary.md](alpha_1_0_test_summary.md), [general_alpha_2_0.md](general_alpha_2_0.md) (крок 02)

## Мета

Гравець **ніколи** не застрягає у мертвій точці. За будь-якого стану (0 EPTS, порожня дошка, розпроданий інвентар) існує ланцюжок дій, що повертає в core loop: продати предмет → безкоштовно пересканувати дошку → взяти посильний контракт → заробити. Неможливість deadlock-у доводиться симулятором, а не лише ручним тестом.

## Відтворення (з тест-звіту)

Свіжий акаунт → витратити весь стартовий баланс → провалити/закрити всі контракти дошки. Результат: 0 EPTS, дошка порожня («NO WIRELESS NETWORKS DETECTED»), кнопка refresh вимагає 10 EPTS і відмовляє, продати нічого не можна, дошка сама не оновлюється. Гра закінчена без Game Over.

## Діагноз (підтверджений читанням коду)

Глухий кут — не один баг, а **замкнене коло з чотирьох фактів**:

1. **Кожна атака закриває контракт назавжди** — успіх чи провал, `attack_repository.dart` ставить `is_completed = 1`. Дошка тільки скорочується.
2. **Оновлення дошки платне і заблоковане при < 10 EPTS.** `TargetRepository.refreshContracts(payFee: true)` знімає `const fee = 10` ([target_repository.dart:70](../../../lib/repos/target_repository.dart)), а `_handleRefresh` у [target_board_screen.dart:69-81](../../../lib/screens/target_board_screen.dart) відмовляє при `currentBalance < 10`. Поріг `10` продубльовано хардкодом у **трьох** місцях (repo, guard екрана, стиль кнопки) — порушення принципу «дані окремо від коду».
3. **`expires_at` пишеться, але ніде не перевіряється.** Контракти отримують `+1 день`, проте `fetchActiveContracts` не фільтрує прострочені й ніщо не регенерує дошку з часом — «дошка не оновлюється з часом» з тест-звіту.
4. **Продажу немає взагалі.** В `InventoryRepository` є buy/upgrade, sell відсутній.

Симулятор alpha 1.0 «довів» неможливість банкрутства (мінімум 22 EPTS), але грав оптимально і не покривав сценарій реального тестера.

Суміжна знахідка (НЕ чіпати в цьому кроці): `ensureCleanUpContract` та Raid-блок дошки працюють — вихід із «wanted 100%» існує; глухий кут суто фінансовий.

## Задачі

### 2.1 Продаж предметів (`InventoryRepository`)

- [ ] `sellSoftware(profileId, userSoftId)` та `sellHardware(profileId, userHardId)` — транзакції за зразком buy/upgrade: нарахувати ціну продажу → видалити рядок `user_software`/`user_hardware` → `_recalculatePowersTxn` → оновити баланс. Повертають нараховану суму (для снекбара).
- [ ] Ціна продажу: `round(sellRatio × (base_price + вкладені_апгрейди))`, де `sellRatio = 0.5` (з конфігу 2.4). Вкладене в апгрейди відновлюється з тих самих джерел, що їх рахує upgrade: для софту — `cost` кроків `level_up_strategy` до `current_level`; для заліза — формула `base_price × 0.6 × lvl` за пройденими рівнями. Жодних нових колонок БД — усе derivable, **міграція схеми не потрібна**.
- [ ] Guard проти нового deadlock-у: **заборонити продаж останнього софт-предмета** (без софту атака неможлива в принципі) — кидати `EconomyException` з людським текстом. Останнє залізо продавати можна (перевірити задачею 2.6, що Resolution Engine коректно живе з `hardware_power = 0`), але з попередженням у UI.
- [ ] UI (Workshop Item, Screen 9.2): кнопка `SELL · +N EPTS` поруч з UPGRADE + діалог підтвердження (сума, для останнього заліза — попередження). Після продажу — повернення на список Workshop (предмета більше немає — залишатись нема на чому; це свідомий виняток із правила «не викидати з екрана» бага №4) + refresh сесії.
- [ ] Продаж не чіпає `wanted`/`black_trust` і не залежить від RISK TAX (податок — на купівлю, штрафувати продаж вдруге — подвійне покарання).

### 2.2 Дошка: безкоштовний аварійний скан + TTL (`TargetRepository` + Screen 5.1)

- [ ] **Безкоштовний скан порожньої дошки.** Якщо активних контрактів 0 — кнопка refresh стає `EMERGENCY SCAN · FREE` і викликає `refreshContracts(payFee: false)`. Платний refresh (10 EPTS) лишається для дострокової ротації непорожньої дошки. Це мінімальна зміна, що розриває коло: гроші потрібні лише щоб *прискорити* ротацію, а не щоб *існувати*.
- [ ] **Увімкнути TTL.** `fetchActiveContracts` фільтрує прострочені (`expires_at < now`); при завантаженні дошки, якщо після фільтрації контрактів 0 — автоматична безкоштовна регенерація ще до першого рендера списку (гравець бачить свіжу дошку, а не порожній екран). TTL (зараз 1 день) — у конфіг 2.4.
- [ ] Прибрати дублювання порога: екран бере плату з єдиного джерела (2.4), а не з трьох хардкодів `10`.
- [ ] Honeypot-логіка при регенерації не змінюється (перевірити, що безкоштовний скан не дає способу «пересканувати пастку в нуль» дешевше, ніж це можливо зараз — безкоштовний шлях доступний лише при порожній дошці).

### 2.3 Страховий контракт (гарантія посильності)

`refreshContracts` вже гарантує ≥1 «easy» шаблон за рівнем, але «посильність» залежить і від софту гравця:

- [ ] Після відбору шаблонів гарантувати, що **≥1 контракт** мапиться (через `_getMissionTypeIdForTargetType` → `primary_soft_type_id`) на тип софту, **яким гравець уже володіє**; якщо жоден — замінити один слот шаблоном під наявний софт. Разом із забороною продавати останній софт (2.1) це закриває інваріант «завжди є що атакувати».
- [ ] Гарантувати мінімальну нагороду страхового контракту: `epts_reward ≥ вартість платного refresh` (щоб один успіх завжди повертав здатність ротувати дошку). Floor — у конфіг 2.4.
- [ ] Сигнатура: `refreshContracts` потребуватиме список типів софту гравця — передавати параметром (`ownedSoftTypeIds`), не тягнути запит всередину, щоб функція лишалась тестованою.

### 2.4 Конфіг економіки — єдине джерело чисел

- [ ] Новий `assets/data/catalog/economy.json`: `board_refresh_fee: 10`, `sell_ratio: 0.5`, `contract_ttl_hours: 24`, `insurance_min_reward: 10`. Завантаження за зразком решти каталогу (`ContentSeeder`/`ContentValidator` — валідація діапазонів), доступ через простий immutable-об'єкт `EconomyTuning` у репозиторіях та екранах.
- [ ] Викорінити хардкоди: `const fee = 10` (repo), `< 10` і `>= 10` (screen), TTL `Duration(days: 1)` (repo), sell ratio.
- [ ] Оновити [catalog/README.md](../../../assets/data/catalog/README.md) описом нового файлу.

### 2.5 Симулятор: сценарій «банкрут»

- [ ] `tool/simulate.dart`: новий сценарій — навмисно програвати атаки до вичерпання балансу і контрактів, потім діяти як гравець у ямі (продати → безкоштовний скан → страховий контракт). Критерій: за ≤ N кроків симульований гравець знову має додатній баланс і непорожню дошку; інакше — exit code ≠ 0.
- [ ] Прогнати основний (оптимальний) сценарій — переконатися, що зміни 2.2–2.4 не зрушили цілі прогресії alpha 1.0 (рівень 2 на атаці №5, рівень 5 на №15). Продаж може злегка збагатити оптимального гравця — якщо зрушення > ~10%, компенсація числами в JSON, не кодом.

### 2.6 Тести

- [ ] Unit (`inventory_repository`): продаж нараховує правильну суму (без апгрейдів / з апгрейдами софту / заліза); рядок видалено; powers перераховано; заборона останнього софту кидає виняток; продаж останнього заліза дозволений.
- [ ] Unit (`resolution_engine`): атака з `hardware_power = 0` — коректний (хай і мізерний) time budget, без ділення на нуль/крашу.
- [ ] Unit (`target_repository`, seeded `customSeed`): безкоштовний скан при порожній дошці; фільтрація прострочених; страхова гарантія — для гравця лише з Phishing-софтом дошка завжди містить ≥1 Data Theft-контракт з нагородою ≥ floor.
- [ ] Unit (конфіг): `economy.json` валідується, значення читаються, дефолти відсутні (відсутнє поле = помилка сіду, не мовчазний фолбек).

## Критерії приймання

- [ ] Сценарій бага №2 непройдений: з будь-якого досяжного стану гравець повертається в core loop без дебаг-інструментів; доведено сценарієм «банкрут» у симуляторі (автоматично) і ручним чеклістом 2.7.
- [ ] Дошка ніколи не лишається порожньою після відвідування екрана (TTL + авто-скан), а платний refresh більше не є єдиним джерелом контрактів.

## Поза межами кроку

- «Гра в борг» / кредити з тест-звіту — не впроваджуємо: продаж + безкоштовний скан закривають потребу дешевше й без нової механіки; повернутися до ідеї лише якщо плейтест кроку 09 покаже, що ями все ще трапляються.
- Конвертація преміум-валюти uep → epts — post-alpha (див. general-план).
- Снекбар-повідомлення цих флоу успадковують поточний стиль; уніфікація снекбарів — крок 03.
- Іконки/оформлення кнопок SELL і EMERGENCY SCAN — пресети кроків 05–06; тут функціональний мінімум.

## Summary

**Виконано 2026-07-04.**

### Задача 2.1 — Продаж предметів (`InventoryRepository`)
- Реалізовано методи `sellSoftware(profileId, userSoftId)` та `sellHardware(profileId, userHardId)`.
- Розрахунок ціни продажу: `round(sellRatio * (basePrice + upgradesCost))` за формулами, де `sellRatio` береться динамічно з файлу `economy.json`.
- Захист від deadlock-у: продаж останнього софт-модуля заблоковано — викидається виняток `LastSoftwareException`. Продаж останнього заліза дозволений (перевірено, що `ResolutionEngine` коректно працює з `hardwarePower = 0`, застосовуючи штраф до часу без крашу).
- UI (Workshop Item Screen 9.2): Кнопка `SELL · +N EPTS` додана поруч із UPGRADE. Створено діалог підтвердження. Для останнього заліза показується попередження про зниження потужності до 0. Після продажу гравець перенаправляється назад до списку Workshop.

### Задача 2.2 — Безкоштовний аварійний скан + TTL (`TargetRepository` + Screen 5.1)
- Додано фільтрацію застарілих контрактів: `expires_at IS NULL OR expires_at > now` у SQL запиті `fetchActiveContracts`.
- Якщо список активних контрактів порожній, `activeContractsProvider` автоматично запускає безкоштовне оновлення дошки `refreshContracts(payFee: false)`.
- UI (Target Board Screen 5.1): Якщо дошка порожня, кнопка оновлення перетворюється на `EMERGENCY SCAN · FREE`. Якщо на дошці є контракти, оновлення коштує `board_refresh_fee` з файлу `economy.json`.

### Задача 2.3 — Страховий контракт
- Під час регенерації контрактів гарантовано, що хоча б один контракт (індекс 0) сумісний із наявними софт-інструментами гравця (через `ownedSoftTypeIds`). Якщо спочатку такого немає, перший слот замінюється на шаблон під наявний софт.
- Гарантовано мінімальну нагороду страхового контракту `epts_reward >= insurance_min_reward` (з файлу `economy.json`).

### Задача 2.4 — Конфіг економіки
- Створено файл `assets/data/catalog/economy.json` з усіма константами.
- Створено клас моделі `EconomyTuning`.
- Здійснено інтеграцію в `ContentSeeder` та `ContentValidator`. Файл економіки валідується під час сіду, а значення записуються в таблицю `meta` як JSON рядок із ключем `economy_tuning`.
- Усі хардкоди `fee = 10`, `Duration(days: 1)` та `sell_ratio` видалені з коду репозиторіїв та екранів.

### Задача 2.5 — Симулятор
- У `tool/simulate.dart` додано новий автоматичний сценарій «банкрут», який перевіряє поведінку гравця в ямі: продається стартове залізо, виконується безкоштовний скан, виконується та успішно завершується страховий контракт.
- Додано автоматичну перевірку прогресії: якщо досягнення рівнів зміщується від оптимального, симулятор завершується помилкою. Усі тести балансу alpha 1.0 пройдено успішно.

### Задача 2.6 — Тести
- Створено файл `test/step02_economy_test.dart` з тестами продажу інвентаря, роботи `ResolutionEngine` з `hardwarePower = 0`, автоматичного скану порожньої дошки, страхових контрактів та конфігу. Усі тести проходять зелено.
