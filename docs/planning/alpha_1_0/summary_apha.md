# Підсумкове рев'ю альфа-версії — The MiddleMen

> Дата: 2026-07-04 · Версія: `0.2.0-alpha.1+2` · Оцінка за результатами виконання всіх 10 кроків плану [general_apha.md](general_apha.md)

---

## Вердикт (TL;DR)

**Проєкт відповідає визначенню MVP/альфи та готовий до внутрішнього тест-релізу** (роздача APK 2–3 тестерам вручну). Повний core loop — *Розвідка → Підготовка → Міні-гра → Наслідки → Апгрейд* — працює на реальних даних без debug-заглушок, обидва цільові білди (Android APK, Windows exe) збираються й запускаються, аналізатор чистий, 83/83 тести проходять, баланс прогресії підтверджено симуляцією.

**Не готовий** до публічного релізу (Google Play / відкрите тестування) — бракує іконки/splash, release-підпису, реальних SFX і живого плейтесту на фізичному пристрої. Це очікувано і нормально для альфи.

Загальна оцінка стану: **8/10 для стадії альфи.** Мінус два бали: недіагностоване зависання трьох widget-тестів (і пов'язаний з цим ризик у CI) та повна відсутність верифікації на фізичному Android-пристрої.

## Оцінка за областями

### Архітектура — сильна сторона ✅

Чітке пошарове розділення, яке реально дотримується, а не лише декларується:

- **`lib/game/resolution/` — чистий Dart без Flutter.** Resolution Engine (серце геймплею) повністю тестується unit-тестами і навіть запускається в CLI-симуляторі (`tool/simulate.dart`). Це найцінніше архітектурне рішення проєкту: баланс можна перевіряти за секунди без запуску гри.
- **Репозиторії** (7 штук, `lib/repos/`) — єдина точка доступу до БД; критичні операції (покупка з RISK TAX) рахуються всередині транзакції, а не з UI, тож видима ціна завжди дорівнює списаній.
- **Контент відділений від коду.** Усі числа балансу — в `assets/data/catalog/*.json`, сідяться в БД через `ContentSeeder` з валідацією (`ContentValidator`). Баланс правиться без перекомпіляції.
- **Riverpod** послідовно: сесія гравця, сесія атаки, репозиторії — через providers; екрани не тримають бізнес-логіки.

Слабше місце: Flame використано лише для однієї міні-гри (це відповідає рекомендації review.md), але інші 3 типи місій ідуть через AUTO-RESOLVE-панель — гравець це бачитиме, і «фан» тримається на одній міні-грі.

### База даних — добре для альфи, з відомим боргом 🟡

Ручна схема SQLite (v6) з міграціями працює і покрита тестом схеми. Але review.md ще на старті рекомендував перехід на **Drift** заради типобезпеки й компільованих запитів — цей борг не погашено і зростатиме з кожною новою таблицею. Для альфи прийнятно; перед бетою варто повернутись до цього рішення, поки схема ще помірного розміру.

### Тести — хороше покриття логіки, діра у widget-шарі 🟡

Unit-покриття найважливішого (Resolution Engine, економіка, wanted-ефекти, level curve, контент-пайплайн, генератор контрактів, хешування паролів) — солідне і швидке. Але:

- **3 widget-тести стабільно зависають** (`economy_widgets_test.dart`, `target_board_widgets_test.dart`, `profile_widget_test.dart`) — комбінація реальної файлової БД + `ConsumerWidget` + `ProviderContainer`; корінь не знайдено за 3 кроки діагностики. Фактично widget-шар зараз перевірений лише одним smoke-тестом (`widget_test.dart`).
- **⚠️ CI-ризик:** `.github/workflows/ci.yml` запускає `flutter test` **без виключень** — якщо ці три тести зависають і на ubuntu-runner, CI висітиме до таймауту GitHub (6 годин) на кожному push. Це треба перевірити першим же push'ем; якщо підтвердиться — тимчасово виключити файли з CI (наприклад, через `dart_test.yaml` tags або перейменування на `*.hang.dart`).

### Стабільність і UX — достатньо для альфи ✅

- Структуроване логування (`AppLogger`: консоль + best-effort файл на пристрої) замість мовчазних `catch (_)`.
- `PopScope` захищає від втрати прогресу атаки апаратною кнопкою «назад»; портретний lock; помилки БД показуються снекбарами і логуються.
- Онбординг: 4 одноразові підказки на ключових екранах — мінімум, але для тестерів із інструкцією вистачить.

### Аудіо/візуал — найслабша область ⬜

- Є лише один BGM-трек (меню, тепер продовжується в хаб). SFX-хуки підключені, але аудіофайлів немає — гра фактично тиха під час дій.
- Немає іконки застосунку і splash-екрана (стандартна Flutter-іконка). Для внутрішніх тестерів не блокер, для будь-якої публічної роздачі — блокер.
- 66.3 МБ APK — великуватий для гри такого обсягу; головний внесок — media_kit заради відео-фону меню. Рішення прийняте свідомо (review.md), але якщо тестери скаржитимуться на розмір — заміна відео-фону на шейдер/анімацію зекономить ~25 МБ.

### Баланс — підтверджений, v1 🟡

Симулятор (`dart run tool/simulate.dart`) підтвердив цілі: рівень 2 на атаці №5, рівень 5 на №15, банкрутство неможливе (мінімум 22 epts), перший бюджетний вибір на атаці №2. Але симулятор грає «оптимально» — реальні гравці гратимуть гірше і повільніше. Числа v1 слід вважати стартовою гіпотезою, яку перевірить лише живий плейтест.

## Ризики (пріоритезовано)

1. **CI може зависнути** через 3 проблемні widget-тести у повному `flutter test` — перевірити на першому push, за потреби виключити. *(зусилля: хвилини)*
2. **Жодного запуску на фізичному Android.** Release-APK зібрано, але поведінка media_kit-відео, продуктивність міні-гри й тач-керування на реальному пристрої не перевірені. Це найбільша невідомість перед роздачею тестерам. *(зусилля: 1 сесія з пристроєм)*
3. **Зависання widget-тестів** — недіагностований корінь може вказувати на глибшу проблему ініціалізації БД/провайдерів, яка колись проявиться і в рантаймі. Підозрюваний фактор: дві паралельні установки Flutter SDK на машині розробника (`C:\Development\flutter` і `C:\flutter_SDK\flutter`). *(зусилля: окрема діагностична сесія)*
4. **«Фан» тримається на одній міні-грі** — якщо Sniffer не зайде тестерам, це найбільший геймдизайн-ризик (він і був позначений таким у плані). Фідбек тестерів по міні-грі — головне питання тест-релізу.
5. **APK підписано debug-ключем** — нормально для ручної роздачі, але не для будь-якого стору; також оновлення поверх майбутнього release-підпису не встане (потрібне переустановлення).

## Рекомендації перед роздачею тестерам

**Мінімум (до роздачі):**
1. Прогнати APK на хоча б одному фізичному Android-пристрої: встановлення, реєстрація, 2–3 атаки, міні-гра.
2. Push у GitHub → переконатися, що CI не висне (ризик №1).
3. Проставити git-тег `0.2.0-alpha.1` (потрібен явний запит — не зроблено автоматично).
4. Додати тестерам коротку інструкцію: що це, як встановити APK з невідомого джерела, на що дивитися (насамперед — чи «фаниться» міні-гра).

**Бажано (не блокує):**
5. Іконка застосунку (навіть проста) — перше враження тестера.
6. 3–4 базові SFX (безкоштовні CC0-паки) — гра зараз беззвучна в діях.

**Після збору фідбеку (напрям на бету):**
7. Рішення по Drift-міграції БД, поки схема невелика.
8. Діагностика widget-тестів + прибирання другого Flutter SDK.
9. Балансування v2 за даними реальних сесій; решта 3 міні-ігор.

## Висновок

За 10 кроків проєкт пройшов шлях від каркаса з wireframe-екранами до цілісної, збираної, тестованої гри з робочою економікою, прогресією, репутаційними механіками і однією повноцінною міні-грою. Архітектурний фундамент (чистий Resolution Engine, контент у даних, репозиторії, симулятор балансу) — вищий за типовий для альфи і дозволить швидко ітерувати баланс та додавати контент без перебудови коду.

Статус: **альфа відбулася; наступний крок — не код, а люди.** Головне, що зараз потрібно проєкту, — 2–3 живі тестери з фізичними Android-пристроями і їхня чесна відповідь на одне питання: чи цікаво грати в «Перехоплення потоку» десятий раз поспіль. Усе інше — полірування навколо цієї відповіді.
