# Технічне рев'ю проєкту The MiddleMen

> Дата: 2026-07-04 · Обсяг: стек, БД, архітектура, безпека, ризики.
> Контекст: одиночна офлайн-гра (Android — основна ціль, Windows — dev-платформа), пре-альфа.

## Резюме

Стек обрано загалом правильно: **Flutter + Flame + SQLite — адекватний фундамент** для мобільної офлайн-гри з реляційною економікою. Кардинально міняти нічого не треба. Головні проблеми не в технологіях, а в архітектурних звичках, які вже закладаються: передача стану через аргументи роутів, один god-class на всю БД, відсутність тестів на майбутню економіку. Це дешево виправити зараз і дорого — після 10 екранів на реальних даних.

Оцінка по областях: технології ✅ · схема даних 🟡 · архітектура коду 🟡 · безпека/якість 🟡

## 1. База даних: лишати SQLite, але через Drift

### Чому реляційна БД — правильний вибір

Схема з db_planning.md — це ~15 таблиць із FK-зв'язками, join-ами (інвентар → каталог → типи), транзакційними операціями (покупка = списання балансу + INSERT інвентарю атомарно). Це класичний реляційний домен. Документні сховища тут програють:

| Варіант | Вердикт | Чому |
| --- | --- | --- |
| **SQLite (поточний)** | ✅ лишати | Реляційність, транзакції, ACID, працює всюди, zero-config |
| Hive / hive_ce | ❌ | Key-value без зв'язків і транзакцій між «таблицями» — покупка предмета стане двома неатомарними записами |
| Isar | ❌ | Швидкий, але проєкт роками у невизначеному стані підтримки; зв'язки слабші за SQL |
| ObjectBox | ❌ | Комерційне ядро, надлишковий для локальної гри |
| Realm | ❌ | MongoDB згорнула офіційний Flutter SDK — небезпечний вибір у 2026 |
| Drift (поверх SQLite) | ✅ **рекомендую** | Та сама SQLite, але типобезпека + міграції + реактивні запити |

### Рекомендація: sqflite → Drift, поки схема мала

Поточний код уже демонструє проблему сирого sqflite: у [database_helper.dart:116-126](../lib/db/database_helper.dart#L116-L126) `l.id AS level_id` мовчки перезаписує `p.level_id` у результаті запиту — помилка, яку Drift зловив би на компіляції. З 3 таблицями міграція на Drift — день роботи; з 15 таблицями після кроку 03 — тиждень.

Що дає Drift конкретно цьому проєкту:

- **Типізовані запити**: join `accounts × profiles × levels` повертає згенерований клас, а не `Map<String, dynamic>` з ручним кастингом (зараз ~60 рядків мапінгу на два запити).
- **Реактивні `watch()`-запити**: баланс epts на Home Page оновлюється сам після покупки в Store — це закриває половину задач state management з кроку 02.
- **Мігратор** із покроковими схемами і тестами міграцій — критично, коли після альфи не можна буде wipe-ити дані гравців (поточна стратегія `_migrate` = DROP усіх таблиць).
- Під капотом та сама sqlite3, тож `sqlite3_flutter_libs`/Windows-налаштування не змінюються.

Якщо міграція на Drift не приваблює — прийнятний план Б: лишити sqflite, але **обов'язково** розбити DatabaseHelper на репозиторії (крок 02) і писати CHECK/FK у SQL. Drift — рекомендація, не блокер.

### Зауваження до схеми (db_planning.md)

1. **JSONB не існує в SQLite** — це Postgres-термін. У SQLite це TEXT + `json_valid()` CHECK + json1-функції. У Drift — `TextColumn` з конвертером у Dart-клас. Треба виправити в документі, щоб не закластися на неіснуючі можливості.
2. **Розбіжність документа з кодом**: у коді profiles є `karma`, `popularity`, але немає `epts_balance`/`uep_balance` — тобто немає головної валюти гри. Документ і код описують різні профілі; звести на кроці 03.
3. `UserSoftware.name UNIQUE` глобально — два гравці не зможуть мати «Hydra Brute». Unique має бути на пару (user_id, item).
4. Каталог (SoftwareItems) і інвентар (UserSoftware) правильно розділені — це добре. Але інвентар має посилатися на каталог (item_id FK), а не дублювати name/max_level/level_up_strategy.
5. Типи цілей як 7 окремих таблиць `persons_scale`, `corporation_scale`… — антипатерн; одна `target_types` + `target_templates` (що і зроблено нижче в тому ж документі — лишити саме цей варіант).
6. Дрібне: файл перейменовано на `db_planning.md` (typos `level_up_strategu`, `UserHardwarare` виправлено).

## 2. Ігровий рушій: Flame — так, але тільки для міні-ігор

Поточна (неявна) архітектура правильна: **UI-екрани — чистий Flutter, Flame — лише всередині Screen 7.2**. Це варто зафіксувати як свідоме рішення:

- 90% гри — це меню, списки, магазини. Flutter робить це краще за будь-який ігровий рушій.
- Кожна міні-гра = окремий `FlameGame`, вбудований через `GameWidget` з чітким контрактом входу/виходу (`AttackSetup` → `MinigameOutcome`).
- Порожній `MiddlemenGame` у `lib/game/middlemen_game.dart` як «гра всього застосунку» — хибний напрям; видалити або перепрофілювати у `SnifferGame`.

Альтернативи (Unity/Godot + embed) для 4 казуальних 2D міні-ігор — надлишкові й ламають єдиний код-бейз. Flame достатній.

## 3. Архітектура коду

### 3.1 Стан передається через аргументи роутів — головний борг

`AccountWithProfile` летить через `ModalRoute.settings.arguments` у кожен екран, а `TargetDetailScreen` отримує голий `int`-індекс хардкод-списку. Наслідки вже видно: після будь-якої мутації профілю (покупка) всі екрани в стеку тримають застарілу копію. Потрібен єдиний джерело правди — сесія гравця у Riverpod (або хоча б ChangeNotifier) + реактивні запити з БД. Деталі — у [planning/step_02](planning/step_02_architecture_state.md).

### 3.2 DatabaseHelper як єдина точка доступу

Зараз 200 рядків на 3 таблиці. З повною схемою це стане 1500+ рядків god-object. Розбити на репозиторії за доменами до розширення схеми, не після.

### 3.3 Дані в коді

Wireframe-и з `static const _items` — нормально для макетів, але список рівнів (Mouse→Wolf) уже зашитий у `DatabaseHelper._seedLevels`, а логіка формування нагород житиме у формулах. Правило для гри з балансом: **усі ігрові числа — в асетах (JSON), код — тільки механіка.** Інакше кожна ітерація балансу = перекомпіляція і ручний прохід.

### 3.4 Тести відсутні

Для UI-макетів — некритично. Але економіка (покупки, resolution атак, wanted) — це чиста логіка, де регресії найдорожчі і тести найдешевші. Мінімальна планка: resolution engine і сервіси покупки/апгрейду покриті unit-тестами з in-memory SQLite (див. кроки 05, 07).

## 4. Безпека та якість

- **SHA-256 без солі** для паролів — для локальної одиночної гри загроза мінімальна (хеш лежить у локальному файлі БД поруч із самим ігровим станом), тож блокером не є. Але: (а) якщо колись з'явиться сервер — це доведеться міняти на Argon2/bcrypt на сервері; (б) додати сіль на акаунт — 5 рядків коду зараз. Чесна альтернатива для офлайн-гри — взагалі прибрати пароль і зробити вибір локального профілю, як у консольних іграх; це знімає і UX-тертя на вході.
- **Wipe-міграція** (`DROP TABLE` на будь-яку зміну версії) — прийнятно у пре-альфі, але має зникнути в останній схемо-змінюючий реліз перед роздачею білдів тестерам: втрата прогресу тестерів = втрата тестерів.
- **media_kit для фонового відео меню** — працює, але це найважча залежність проєкту (+~20–30 МБ до Android-білда, нативні бібліотеки на кожну платформу) заради декоративного лупа. До альфи виміряти розмір APK; якщо > ~80 МБ — замінити на секвенцію кадрів/анімований шейдер/Rive і викинути 3 залежності. На Windows-dev це не заважає, рішення можна відкласти.
- **CI немає** — один GitHub Actions workflow (`analyze` + `test`) окупається одразу (крок 01, залишок).

## 5. Що НЕ треба міняти

- **Flutter** — правильна платформа для UI-важкої гри з ціллю Android+Windows.
- **SQLite** як сховище — правильний клас рішення (питання лише в обгортці, див. §1).
- **Розділення екранів по файлах, іменовані роути, GameScaffold** — здорова база.
- **shared_preferences для налаштувань** — саме те; не тягнути налаштування в SQLite.
- **JSON-асети для контенту** (legends.json) — правильний патерн, масштабувати його на весь ігровий контент.
